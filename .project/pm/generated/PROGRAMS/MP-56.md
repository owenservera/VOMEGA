## Explanation

MP-56 turns observed behavior into durable tests. It takes a trace — a recorded sequence of runtime, browser or provider events — and pushes it through a pipeline: a canonical trace/event contract, normalization and privacy reduction, deterministic fixture generation, replay as regression tests, and eventually continuous harvesting so that every meaningful failure leaves a falsifier behind. Synthetic traces come first; live-provider traces are a later, separately gated variant.

It is deliberately adjacent to, not a copy of, MP-55. A failure capsule freezes one observed failure so another worker can diagnose it. MP-56 converts the behavior that mattered into a byte-stable, replayable fixture that the project's own test runner can execute forever after. Together they stop the same provider or runtime lesson from being relearned by memory and discipline alone.

Today there is no bridge from observed reality to durable tests. Per .project/REALITY.md, browser/provider message behavior in the current seed is fixture/simulated replay with no live control path, and observed behavior is ephemeral: once a debugging episode ends, its evidence walks out with it. MP-56 is that bridge — and it is honest about the seam: a fixture proves that the pinned property replays deterministically; it is never live evidence that the real provider still behaves that way.

## Problem — why this program exists

Without MP-56, every lesson about runtime or provider behavior is relearned by hand. .project/REALITY.md records that browser/provider message behavior in the current seed is fixture/simulated replay with no live control path, and that observed behavior is ephemeral — the same provider/runtime lesson is paid for again each time because nothing converts an observed episode into a durable falsifier. Development acceleration hypothesis #6 (Regression Harvesting) names the cost: the test suite grows from memory and discipline alone instead of from actual pain. The result is recurring failure cost, repeated rediscovery, and regression coverage that lags the reality the project actually observes.

## Objectives

1. Define a provider-neutral trace/event envelope with canonical identity, order, source, evidence and privacy fields such that two representations of the same trace canonicalize to identical bytes.
2. Redact and minimize traces safely while preserving the behavioral property being pinned, with explicit redaction rules and a loss report per trace.
3. Generate deterministic, byte-stable, replayable fixtures from synthetic traces first, excluding generated fixture payload volume from implementation LOC estimates.
4. Replay fixtures in the project's own test/conformance suites so that trace -> fixture -> replay reproduces the pinned property.
5. Convert repeated discoveries — failures, manual successes, provider observations — into permanent regression assets that promote through the project's own proof engine.
6. Keep live trace harvesting explicitly out of scope until an actual live trace source exists together with consent/evidence boundaries.

## Final Ω vision contribution

Serves VISION.md pillar 4 — durable Work, proof and continuity: consequential activity should leave reconstructable evidence, and the environment should hold an honest epistemology of what it actually knows happened. MP-56 is the development-side instance of that pillar: ephemeral observation becomes a durable, replayable proof artifact whose lineage — trace source, redaction loss report, pinned property — remains inspectable rather than opaque, matching VISION's evolution-and-learning requirement that learning improve behavior without silently mutating meaning. The contribution is bounded by PROOF-AND-MATURITY: fixture proof is not live proof, so MP-56 multiplies deterministic coverage without letting anyone claim a real provider behaves a certain way because a fixture passes.

## Boundaries / anti-goals

- Never report a fixture replay as live provider evidence; per PROOF-AND-MATURITY, fixture proof and live proof are distinct maturity levels and must not be collapsed.
- Never weaken merge or release gates; harvested fixtures add falsifiers, they do not replace broader merge/release test gates (see MP-60 test-selection boundary).
- Redaction must preserve the behavioral meaning of the pinned property; no silent semantic loss — every sanitization produces a loss report.
- The live-provider path requires an actual live trace source with a consent/evidence envelope and is out of scope until both exist; it is referenced only as an external dependency (MP-25 protocol work), never built speculatively.
- MP-56 must not become a second failure-diagnosis system (that is MP-55) or a second repository-analysis/parser system (that is MP-21); it consumes their outputs rather than duplicating them.
- Generated fixture/data volume is never counted as implementation LOC and never grades workers.

## Success conditions

- Two representations of the same trace canonicalize to identical bytes (MP56-G1 realized).
- A sanitized trace provably retains its pinned target property, contains zero forbidden-data occurrences, and carries a loss report (MP56-G2 realized).
- The same synthetic trace generates a byte-identical fixture twice, and that fixture replays (MP56-G3 realized).
- A replayed fixture reproduces its pinned property in the project's own test runner (MP56-G4 realized), unlocking MP60-P3 runtime/test-observed edges.
- A seeded observed failure flows to a candidate fixture whose regression gate reaches the promoted state in the project's own proof engine (MP56-G5 realized).
- The test suite demonstrably grows from actual observed pain rather than from memory and discipline alone.

## Falsifiers / open questions

- If normalization cannot preserve a meaningful class of target behaviors while removing forbidden data, the redaction approach needs redesign (redirect P2).
- If generated fixtures are too brittle to survive normal host evolution — high maintenance per fixture — fixture-from-trace may reduce to targeted reproducers only (reduce scope).
- If trace -> fixture -> replay does not reproduce pinned properties more cheaply or reliably than hand-written tests, the pipeline may be split so only high-value trace classes are harvested (split).
- If no live trace source ever becomes available under consent/evidence boundaries, the live variant of P3 and live harvesting in P5 retire, leaving a synthetic-only program (retire parts).
- If harvested fixtures rarely catch regressions once the suite accumulates them, continuous harvesting (P5) may be retired under the accelerator evidence rule in PROOF-AND-MATURITY.

**MP56-P1 — Trace/event contract**

- risk: The contract may over-fit to simulator event shapes and need revision once a real trace source appears.
- risk: Canonicalization must handle unordered or duplicate events without inventing an order that the source did not witness.
- open question: Which event sources must the envelope cover first — host runtime, browser fixture replay, or the provider simulator?
- open question: Should the envelope reuse the shared identity concepts named in FIRST-FIVE-SEED (TraceRef, EvidenceRef, ArtifactRef, repository HEAD, provenance class) rather than inventing a parallel scheme?

**MP56-P2 — Normalize + privacy reduce**

- risk: Redaction may silently destroy the behavioral property being pinned; the loss report and redaction test must make such loss visible rather than assumed away.
- risk: Normalization may strip variability the fixture actually needs to reproduce the original failure.
- open question: What forbidden-data classes are in scope for the redaction scan — credentials, tokens, account/session identifiers, user content?
- open question: Who or what pins the 'target behavior' for a given trace, and where is that pin recorded?

**MP56-P3 — Fixture generation**

- risk: Fixture generation validated only against synthetic traces may not generalize to real trace shapes when a live source eventually exists.
- risk: Generated fixture payload volume could mislead effort accounting if not kept separate from implementation LOC, contrary to the LOC protocol.
- open question: Where do generated fixtures live so they count as test evidence but stay excluded from implementation LOC estimates?
- open question: What makes a fixture replayable against the current host — a recorded message replay against the existing fixture/simulated browser path, or a host API contract?

**MP56-P4 — Replay + regression**

- risk: Replay may depend on host internals that change over time, making harvested fixtures brittle.
- risk: A passing replay must be reported as fixture evidence only; any drift toward treating green replay as live provider behavior would violate the proof boundary.
- open question: Which runner or proof engine owns the replay assertion, and how does it link to Ratchet-gated evidence without duplicating proof state?

**MP56-P5 — Continuous harvesting**

- risk: Automatic harvesting could flood the suite with low-value fixtures, imposing maintenance cost that outruns the regression value (contrary to the regression-harvesting hypothesis).
- risk: The live harvesting path risks being built against a trace source that never exists if consent/evidence boundaries are not resolved first.
- open question: What promotion threshold keeps harvested fixtures valuable rather than noisy?
- open question: What is the minimal consent/evidence envelope a live trace source must satisfy before P5 may touch it, and how does that interact with the MP-55 capsule capture path?
