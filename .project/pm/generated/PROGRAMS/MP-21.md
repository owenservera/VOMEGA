## Explanation

MP-21 is a read-first migration and conformance utility (working name: Reflection Migrator) that points at the existing Ω source tree and answers what the code already proves about itself: which plugins, contributions, routed operations, schemas, config keys, language frames and visual roles exist, which source symbols own each fact, which public behaviors have no self-description, and which descriptions are prose-only rather than structurally grounded. Its role in one line: audit → extract → map → propose → verify. Every extracted fact is bound to a SourceAnchor — repository, commit, content hash, path, symbol — so self-knowledge is reproducible at a pinned HEAD.

It is deliberately not a documentation generator, README scraper, second registry, LLM semantics inventor, source-code authority or silent code rewriter. Facts and meaning stay mechanically separate: directly encoded claims are tagged PROVEN_STRUCTURAL (or DECLARED / INFERRED_SAFE), while titles, capability groupings and relationship ideas stay CANDIDATE_SEMANTIC until a human accepts them. The default is read-only; any proposed source change is explicit, previewable, diffable, test-gated and reversible, and the tool never gains authority to accept its own proposals.

The problem it exists for: the current baseline is already rich in structure (one manifest format, contribution kinds, risk declarations, source-side operation registration, explicit schemas, provider realization records), but its self-description still lives in prose — manifest descriptions, contract-level doc strings, plugin descriptions — which the design itself forbids treating as stronger than executable declarations. Manifest↔runtime op parity is not mechanically checked, duplicated schema/help definitions drift silently, and config parsing is a likely blind spot. Today a fresh worker or agent must reread the repo or trust a narrative to know what the system can actually do.

Within the first five, MP-21 is the substrate: its stable queryable Reflection Graph (MP21-G3) is what MP-54 source-aware bundles, MP-55 structural enrichment and MP-60 impact/test-selection all consume, so the five programs do not build competing parsers or identity schemes. Migration proceeds audit-first in waves, with the MVP semantic slice (Provider, Account, Model, prompt.send) as the first compliance target rather than a full-repo rewrite.

## Problem — why this program exists

Without MP-21, VOMEGA keeps paying three costs. Truth: self-description lives in prose — manifest description strings, contract doc strings, plugin descriptions — which the Reflection design explicitly forbids treating as stronger than executable declarations, yet nothing else distinguishes prose-only claims from structurally grounded ones; manifest↔runtime parity (declared-but-unimplemented ops, implemented-but-undeclared ops, invisible dynamic registration) is not mechanically checked, and duplicate definitions of the same parameter across schema, help text and language frames drift silently. Capability: agents and fresh workers cannot deterministically answer which operations, schemas, config keys or visual roles exist without rereading the repo or trusting a narrative — the migrator doc's §3 question list is currently answerable only by manual reading, and config parsing is a likely blind spot. Time: every downstream accelerator that needs structural understanding (MP-54 context bundles, MP-55 failure enrichment, MP-60 impact/test selection) would otherwise rebuild its own parser and identity scheme — the exact duplication the first-five seed forbids — and migration of the codebase to source-native self-description would happen ad hoc, unsafely, or not at all.

## Objectives

1. Give every structurally knowable public behavior — plugin, contribution, registered operation, schema, config key, language/visual contribution — a stable source-bound identity (SourceAnchor: commit + contentHash + symbol) that is reproducible: repeated scans at the same HEAD yield identical identities.
2. Extract structural facts deterministically from manifests, contracts, op registration, schemas, config parsing, language and visual contributions and tests, tagging each fact with its claim class (PROVEN_STRUCTURAL, DECLARED, INFERRED_SAFE, CANDIDATE_SEMANTIC, COMMENTARY, CONFLICT) and emitting explicit unknowns instead of invented semantics.
3. Build a read-only, queryable Reflection Graph — a derived build artifact, not an authored Wiki database — whose stable entity refs and relations external consumers (MP-54 source-aware bundles, MP-55 structural enrichment, MP-60 impact queries) resolve without reparsing source.
4. Keep extracted facts and suggested meaning mechanically distinct by construction, so no LLM- or heuristic-proposed title, capability grouping or relationship is ever indistinguishable from an extracted fact.
5. Compute manifest↔runtime parity (DECLARED+IMPLEMENTED / DECLARED, IMPLEMENTATION NOT FOUND / IMPLEMENTED, NOT DECLARED / DYNAMIC — NEEDS EXPLICIT REFLECTION PROVIDER) and surface duplicate semantic truth (a schema redefined in help text or language frames) as named drift risks.
6. Turn missing self-description into explicit, severity-ranked gaps with source-native migration proposals that are proposal-only, previewable, diffable, test-gated and reversible, with no-write as the default.
7. Bring the MVP semantic slice — Provider, Account, Model, prompt.send, registration commands, language frames, command validator, VisualSpec — to source-native Reflection compliance without blocking on full-repo migration, and make incremental completeness checkable without the utility becoming source authority.

## Final Ω vision contribution

Grounds primarily in pillar 1 (human semantic execution language) and pillar 5 (governed self-extension/evolution), with supporting grounding in pillar 3 (governed action), pillar 4 (durable Work/proof/continuity) and pillar 10 (capability multipliers). Pillar 1 requires the bridge 'human expression ↔ canonical meaning ↔ deterministic execution' to be inspectable, addressable and deterministic at the semantic/execution boundary; MP-21 supplies exactly that for the environment's own capabilities — operations, schemas, config and contribution boundaries become source-anchored referents the semantic language can resolve without trusting prose. Pillar 3 separates what was said from what was meant and what was allowed; MP-21 applies the same discipline to self-description, keeping proven structural truth mechanically distinct from AI-suggested meaning so probabilistic interpretation never silently becomes consequential authority. Pillar 4's honest epistemology — 'what does VIVIM actually know happened?' — extends here to 'what does VIVIM actually know it can do?', with source anchors making that evidence reconstructable across worker and model replacement. Pillar 5 requires the environment to change itself while preserving identity, evidence and continuity: the migrator proposes safe source-native migrations but never self-accepts them and never rewrites by default. Pillar 10: one extracted graph serves MP-54, MP-55 and MP-60, making the next use materially cheaper instead of accumulating five separate parsers and identity schemes.

## Boundaries / anti-goals

- Not a documentation generator.
- Not a README scraper presented as truth.
- Not an LLM that invents plugin semantics.
- Not a second registry.
- Not a source-code authority.
- Not a code-rewriting agent with permission to silently alter behavior.
- Not a universal ontology inference engine.
- Extract facts; propose meaning; never fabricate proof — suggested meaning stays candidate until accepted and is never a structural claim without deterministic confirmation or review.
- Read-only by default; it never gains authority to accept its own proposals, and compliance must never become documentation bureaucracy rather than structural transparency.

## Success conditions

- Against a pinned checkout, two consecutive scans produce an identical SourceAnchor/digest set and an identical extracted fact set (MP21-G1, MP21-G2).
- A hand-checked sample of extracted facts shows zero invented facts, and every fact traces to an exact source symbol/content anchor.
- An external consumer (MP-54 bundle or MP-60 impact query) resolves stable entity refs and relations from the graph alone (MP21-G3).
- Output separates extracted/PROVEN_STRUCTURAL classes from suggested/candidate classes by construction, checked by test (MP21-G4).
- Gap reports identify missing operation declarations, missing source anchors, duplicate schemas, prose-only claims and source conflicts with per-plugin drill-down.
- The MVP semantic slice powers at least one real contextual Wiki projection generated with no separate Wiki files.
- A seeded structural drift is caught by the compliance check, which itself claims no authority over source (MP21-G5).
- Rerunning after changes shows measurable completeness improvement over the previous run.

## Falsifiers / open questions

- README or other prose is treated as stronger than executable declarations.
- Capability semantics are invented to reach 100% coverage.
- The utility rewrites source by default, or generated Reflection cannot be traced back to source.
- Dynamic op registration becomes invisible in extraction or parity output.
- Config/help schemas remain duplicated after a detected migration opportunity.
- LLM suggestions become indistinguishable from extracted facts.
- A successful migration silently changes runtime behavior.
- Runtime Wiki consumption requires reparsing the entire source tree live, or compliance becomes documentation bureaucracy rather than structural transparency.
- Cross-program: if MP54-P2, MP55-P3 and MP60-P2 satisfy their needs without MP21-G3, the accelerator role of MP-21 shrinks to internal tooling and the program should be reduced or refocused.
- Estimate: if P2 extraction cannot reach determinism at one HEAD within or near the 1,800–3,500 LOC band, the extraction surface set should be cut and re-sequenced rather than shipped non-deterministic.

**MP21-P2 — Structural extraction**

- open question: How far config extraction can go mechanically before the tool must mark unknown and request an explicit declaration.

**MP21-P3 — Reflection Graph + query API**

- risk: This is the program's critical unlock: MP54-P2, MP55-P3 and MP60-P2 all wait on MP21-G3, so a wrong query-API shape propagates widely.
- risk: EntityRef/edge schema must converge on the shared accelerator concepts (SourceAnchor, EntityRef, TestRef, HEAD, provenance class) rather than becoming a second competing identity scheme.
- risk: Temptation to serve runtime queries by reparsing the tree live; the descriptor-plus-live-state model from the Wiki relationship section must hold.
- open question: Exact EntityRef/SourceAnchor schema to be co-designed with MP-54 and MP-60 consumers before the query API freezes.
- open question: Descriptor refresh cadence and staleness policy: what joins to live runtime state versus the build artifact.

**MP21-P4 — Gap + migration proposals**

- risk: Gap priority scoring is a migration aid only; it must not become product-priority or scheduling authority.
- risk: Proposal quality: safe versus poor transformation candidates must follow the migrator doc's own lists or the tool drifts into semantic invention.
- risk: CONFLICT is an output, never silently resolved; a high conflict volume could make reports unusable.
- open question: Which of the good-candidate automatic transformations (anchor metadata, schema-referenced help, obvious static IDs, shared declarative helpers, conformance tests) qualify for automatic patch generation first.
- open question: Whether the gap severity taxonomy needs its own conformance test so ranked proposals cannot masquerade as authority.

**MP21-P5 — Continuous compliance**

- risk: Compliance becoming documentation bureaucracy rather than structural transparency — the design's own named failure mode.
- risk: Binding the check where it could duplicate or usurp Ratchet's external ownership of atomic execution/proof state.
- risk: Threshold tuning: too strict blocks the MVP slice and normal iteration; too lax lets opacity through.
- open question: Where the compliance hook binds (Ratchet gate versus plain CI) without duplicating Ratchet authority.
- open question: What completeness floor applies to new/modified public behavior, and whether the MVP semantic slice gets a separate floor before full-repo migration.
