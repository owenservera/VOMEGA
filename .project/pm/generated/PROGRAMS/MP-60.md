## Explanation

MP-60 is an impact graph and query layer over the VOMEGA codebase: it answers "if this change lands, what else is affected?" It combines structural dependencies (contracts, schemas, registrations, code/test relations) with observed runtime and test participation to name the downstream entities a source change can touch.

It is deliberately not independent infrastructure. It reuses MP-21's Reflection Graph — stable structural identities, edges and query primitives (unlocked by MP21-G3) — as its structural base, and joins observed evidence from MP-56 outputs (normalized traces, fixtures, replay records) as runtime/test edges. It never parses source itself and never becomes a second identity scheme.

On top of structure and observation it ranks the smallest high-confidence affected-test set for fast local iteration. The full suite always remains the merge/release gate; selection is proven in shadow mode against a seeded dependency-class list before anyone relies on it for anything beyond the inner loop.

The final phase is predictive: using accumulated change/test/failure history to estimate blast radius and safe parallelism, validated against named historical changes. Because this phase is graded E4-E5, the PM correction requires a decomposition review before direct execution — that review is recorded as its exit gate.

## Problem — why this program exists

Without an impact graph, every change costs whole-repo reconstruction and full-suite reasoning: an agent touching one contract must re-read enough of the repository to guess at consequences, then run (or fear running) the entire suite to feel safe. Agents cannot see consequences before editing, so parallel workers either over-serialize behind the merge gate or collide because nobody could compute blast radius; the repo's coordination cost is documented in .project/ratchet/DESIGN.md §1. Truth also suffers: "which tests cover this route?" is answered by memory and folklore rather than joined evidence, so verification is either wasteful (always full suite) or dishonest (guessed subsets). This cost compounds as VOMEGA grows toward Ω.

## Objectives

1. Define the concrete impact questions developers and agents need answered before a change, recorded as a named acceptance corpus that can grade candidate answers.
2. Build the static structural impact graph strictly as a projection over MP-21 Reflection identities and edges — a known source change resolves the expected downstream entity set, with no second parser or identity scheme.
3. Join observed runtime/test participation (MP-56 traces, fixtures, test-run records) to named structural graph entities so coverage claims come from evidence, not folklore.
4. Produce a ranked smallest high-confidence affected-test set for inner-loop changes, proven in shadow comparison to catch every member of a seeded dependency-class list.
5. Keep the full suite as the unchanged merge/release gate: selection changes only what runs locally or early, and zero gate definitions change because of MP-60.
6. Validate predictive blast-radius estimation against a named set of historical changes and earn continuation under the acceleration scorecard (MP-67 reference).
7. Keep every impact answer descriptive and source-attributed: the graph reports consequences and recommendations but never authorizes, blocks, or schedules work.

## Final Ω vision contribution

Grounded in seed-docs/VISION.md pillar 5, governed self-extension/evolution: "When the environment changes itself, it should retain enough evidence and lineage to explain what changed, why, what was affected, what was verified, and what remains uncertain." MP-60 is the mechanism that makes "what was affected" computable rather than asserted — a precondition for Ω extending or repairing itself without privileged exceptions. It also serves pillar 4 (durable Work, proof, and continuity): observed runtime/test edges are an honest epistemology of what the environment actually knows exercises a code path, replacing guessed coverage with joined evidence. As a development accelerator it is a capability multiplier per VISION.md's strategic design shape: one impact layer cheapens context bundles (MP-54 P4), regression harvesting (MP-56), failure diagnosis (MP-55), and every future governed self-change, while the graph itself stays descriptive so authority never silently mutates as a side effect of better prediction.

## Boundaries / anti-goals

- Never weakens merge/release gates: selected test sets are for fast local/inner-loop iteration only; the full suite remains the merge and release gate, and selection must be shadow-proven against a seeded dependency-class list before it influences anything beyond the local loop.
- The graph is descriptive, not authority: it reports consequences, coverage and estimates; it never authorizes, blocks, prioritizes, or schedules work, and it grants no PM-style decisioning power.
- No second parser: MP-60 must reuse MP-21's structural identities and edges (MP21-G3) and MP-56's normalized trace/fixture outputs; it must not build its own source parser, entity identity, or competing repository-analysis scheme.
- No speculative framework: the acceleration scorecard governs continuation — P5 predictive impact must measurably earn its place or be reduced/retired rather than persisting as architecture.
- No fabricated observation: runtime edges come from actual traces, fixtures, and test-run records only; fixture-derived edges are never reported as live behavior.

## Success conditions

- A developer or agent can query, for a named source change, the expected downstream structural entity set and receive it in bounded time without re-reading the repository.
- Observed test execution records join to named graph entities, so "which tests cover this route?" returns evidence-backed answers.
- Shadow comparison shows the selected test set catches every member of a seeded dependency-class list while merge/release gate definitions remain byte-for-byte unchanged.
- Real change work consumes impact answers before editing (visible in task/bundle usage), reducing whole-repo reconstruction episodes.
- A blast-radius estimate is validated against a named set of historical changes, with the E5 decomposition review recorded before execution.
- MP-60 survives an acceleration-scorecard check: it measurably reduces validated delivery time, rediscovery, or verification cost compared with the always-full-suite baseline.

## Falsifiers / open questions

- Shadow comparison shows selected test sets missing seeded dependency classes at meaningful rates — reduce scope to descriptive impact only, or tighten the gate before selection is trusted anywhere.
- MP21-G3 slips or the Reflection Graph proves unsuitable as a structural base — redirect the reuse assumption for review with MP-21; do not rescue MP-60 by building a second parser.
- Observed runtime edges prove too noisy or expensive to join reliably (MP56-G4 weak or absent) — restrict MP-60 to static plus test-declared edges and retire the runtime-edge ambition.
- P5 predictive estimates fail the acceleration scorecard (no measurable reduction in validated delivery time or escaped regressions beyond static analysis plus selection) — retire or shrink P5.
- The acceptance corpus shows agents do not actually need impact answers during real change work — split or merge the descriptive layer with MP-54 context bundles and stop standalone investment.

**MP60-P1 — Impact query model**

- risk: Query design without running consumers may capture imagined questions rather than what developers/agents actually ask during real change work.
- risk: Early query assumptions could hard-code entity expectations that conflict with MP-21's eventual Reflection model; the informational soft-dependency into MP-21 design mitigates but cannot eliminate this.
- open question: Should the acceptance corpus be seeded from recorded development episodes (e.g. task/Ratchet history) or authored fresh from anticipated questions?
- open question: Which corpus questions are mechanically gradeable (expected entity sets, known coverage answers) versus human-judged?

**MP60-P2 — Static structural impact graph**

- risk: Second-parser drift: when Reflection coverage is incomplete, the temptation is to reparse source inside MP-60 — this violates the reuse boundary; coverage gaps must route back to MP-21 as gaps, not be re-derived here.
- risk: The Reflection Graph may lack edge types the impact questions need (e.g. test-to-source containment, registration wiring); new relation primitives must be negotiated with MP-21 rather than invented locally.
- risk: Graph freshness/rebuild cost on a growing repo could make answers stale relative to HEAD; staleness handling is unresolved.
- open question: Which relation types (imports, contract/schema use, operation registration, config binding, test containment) must the projection cover to satisfy the MP60-G1 corpus?
- open question: How should HEAD-binding and staleness be surfaced in every impact answer so consumers know which revision the graph describes?

**MP60-P3 — Runtime/test-observed edges**

- risk: Without MP56-G4 there are no trustworthy live traces; only synthetic/fixture-derived edges are possible, which join cleanly but cover less real behavior.
- risk: Trace-to-entity joins may be ambiguous (one observed event maps to several candidate entities), producing noisy edges that later mislead test selection.
- risk: Edge volume from repeated runs could bloat the graph without improving answer quality; retention/decay rules are undefined.
- open question: What minimum provenance (MP-56 normalized fixture vs raw trace vs bare test-run record) is required before an observed edge is trusted and surfaced in answers?
- open question: How should observed-edge confidence and decay be represented so stale execution records do not overstate current coverage?

**MP60-P4 — Affected-test selection**

- risk: Gate-weakening drift: any mechanism that lets a selected subset silently replace the full suite would weaken merge/release truth; selection must remain shadow-only, compared against the full suite, until MP60-G4 proves it, and even then it must never alter gate definitions.
- risk: Coverage evidence for rarely-run routes may be sparse, so selected-set confidence could be overstated exactly where changes are riskiest.
- risk: Convenient fast selection may train workers to skip broader verification habits — a behavioral risk the shadow comparison does not itself detect.
- open question: What recall threshold against the seeded dependency-class list qualifies a selected set as high-confidence enough to recommend for the inner loop?
- open question: Where does the selected set run (local loop, PR annotation, Ratchet suggestion) such that merge/release gate definitions remain untouched?

**MP60-P5 — Predictive impact/concurrency**

- risk: E5-grade work executed directly without decomposition would violate the PM correction (§9: an E5 grade requires a decomposition review before direct execution); needsReview and the MP60-G5 exit gate exist precisely to force that review first.
- risk: Predictions learned from limited early history may overfit and express false confidence in blast radius or safe parallelism.
- risk: A predictive layer can drift toward decisioning (auto-scheduling or auto-clearing parallel work); it must remain advisory, with estimates validated against named historical changes before influencing anything.
- open question: How much accumulated change/test/failure history is required before blast-radius estimates are validated rather than anecdotal, and which named historical changes form the validation set?
- open question: What decomposition splits MP60-P5 into reviewable units of E3 or lower, and who performs the required decomposition review?
