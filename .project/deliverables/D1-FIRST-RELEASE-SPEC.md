# D1 — Executable First-Release Semantic Twin

Status: **SELECTED FIRST BUILD DELIVERABLE**  
Date: 2026-10-06  
Product relation: development release supporting the owner-selected floating-command-box public release.

## 1. Release claim

D1 proves that the narrow first-release interaction can exist as **one executable semantic system** before live provider automation is introduced.

The claim is:

> Given a pinned synthetic World and ordinary-language input, Ω can produce explicit semantic meaning, preserve material ambiguity, accept equivalent textual or visual correction, validate deterministically, project grounded help, execute a governed virtual capability, emit explicitly simulated evidence, and replay the result deterministically.

D1 does **not** claim:

- live Provider support;
- browser control;
- authenticated Account identity;
- Windows-native product packaging;
- public-beta readiness;
- durable background Work;
- Forge/evolution;
- Canvas/spatial UI;
- provider healing.

## 2. User/developer experience

D1 should be launchable as a local developer product twin. The exact UI technology is open.

The minimum visible surface has:

- text input;
- current interpretation;
- Provider / Account / optional Model route;
- validation state;
- unresolved choices;
- consequence/effect preview;
- semantic correction controls;
- contextual help;
- execution state;
- evidence/result panel;
- replay/session inspector suitable for development.

It may visually resemble the future floating box, but native Windows chrome, tray, hotkey and installer are not D1 requirements.

## 3. Canonical journey

A complete acceptance scenario:

### World W-D1

Synthetic fixture state begins with:

- Provider: Claude;
- no Accounts;
- capability definition: `prompt.send`;
- virtual realization available only after a compatible Account exists;
- authority fixture that requires a bounded consent decision for the simulated external-transfer effect.

### Journey

1. User enters: **“add my Claude work account”**.
2. Ω interprets this as Account registration/configuration through the same semantic command path used by other actions.
3. Synthetic `Claude Work` relationship appears.
4. User enters: **“add another Claude account and call it Personal”**.
5. Synthetic `Claude Personal` appears.
6. User enters: **“Ask Claude to explain this error: build failed”**.
7. Ω identifies `prompt.send` and Claude but does **not** silently choose between Work and Personal.
8. UI exposes the unresolved Account.
9. Branch A: user types **“use Work”**.
10. Branch B from the same pre-choice state: user clicks/selects **Claude Work**.
11. Both branches converge on equivalent canonical command identity/digest.
12. Consequence projection shows that payload content would cross the simulated provider boundary.
13. Command becomes READY only after all required fields and authority requirements are satisfied.
14. Contextual help can explain Provider, Account, `prompt.send`, why a choice was required, and what SIMULATED means.
15. User commits execution.
16. Virtual `prompt.send` produces deterministic simulated events and receipt.
17. Receipt is structurally incapable of being confused with live provider evidence.
18. Complete session is replayed from pinned artifacts and produces the same semantic command/evidence digest.

## 4. Required semantic slice

D1 needs only enough semantic substrate for:

- Provider;
- Account;
- optional Model field admitted by the command shape but not required for the canonical journey;
- Capability;
- Realization;
- World snapshot/version;
- interpretation revision;
- semantic edit;
- command;
- consequence;
- authority fixture;
- virtual execution;
- evidence;
- semantic handle for UI/Wiki projection.

Do not solve the entire future ontology.

Stable distinctions that must survive:

```
Provider ≠ Account ≠ Model ≠ Session
Capability ≠ Realization
Natural language ≠ canonical command
Canonical command ≠ authority
Consequence ≠ authority
Evidence ≠ authority
World ≠ Surface
Confidence ≠ proof
Simulation ≠ live external evidence
```

## 5. Required command behavior

D1 must establish a candidate release-level `USE`/command representation sufficient for the journey.

It must carry or resolve the equivalent of:

- capability;
- Provider;
- Account;
- optional Model;
- parameters/payload;
- context refs;
- world version;
- interpretation revision;
- unresolved requirements;
- consequence;
- authority requirement/decision;
- selected realization;
- expected evidence;
- deterministic identity/digest.

The field spelling and serialization remain engineering choices.

### READY law

A command is READY only if every field required by the selected capability/realization is resolved and compatible, no material ambiguity remains, the World version is valid for the decision, and the required authority state permits commitment.

The current false-READY corpus case `U1` must turn red-to-green rather than be hidden or deleted.

## 6. Synthetic World requirements

D1 fixtures must be source-labelled and impossible to confuse with observed state.

At minimum provide deterministic fixtures for:

- empty/no-account World;
- one Claude Account;
- two Claude Accounts;
- stale/unavailable Account;
- incompatible/unknown target;
- optional Provider/Model routing case for regression/generalization.

Each World must have deterministic identity/digest.

Fixture state must never be presented as current provider reality.

## 7. Realtime/revision requirements

Each meaningful text change produces a revision identity.

Required behavior:

- older asynchronous interpretation cannot overwrite newer input;
- semantic handles refer to the active revision;
- a correction creates an explicit semantic edit/recompile, not hidden UI mutation;
- running/committed execution remains bound to the command revision that was committed;
- replay can reconstruct the chosen path.

## 8. UI/projection requirements

The UI consumes a deterministic semantic projection; it does not parse language itself.

It must visibly distinguish:

- interpreted;
- unresolved;
- unavailable;
- READY;
- consent/authority required;
- executing;
- completed simulated;
- failed simulated;
- uncertain simulated, if exercised.

At minimum the route projection shows:

`Capability → Provider → Account → optional Model → Realization`

Presentation may vary without changing command meaning.

## 9. Typed/clicked parity

Choosing `Claude Work` through text and choosing it through UI must result in equivalent semantic edits and the same canonical command digest under the same World/revision basis.

The UI is not allowed a privileged action callback that bypasses the command machinery.

## 10. Contextual help / Wiki slice

D1 needs a **minimal source-bound Reflection → Reflection Graph → contextual Wiki/help slice**, not the complete Reflection program.

The help system must derive structural claims from actual D1 source/declarations through a deterministic read-only extractor/Reflection representation, then join those facts with active World/interpretation state. A separately authored Wiki/help database is not authoritative.

Minimum D1 Reflection scope:

- `prompt.send` capability and required parameters/slots;
- D1 virtual realization;
- relevant Provider/Account semantic types;
- relevant consequence/evidence semantics;
- semantic Account-selection action(s);
- stable source anchors/content digests binding reflected facts to implementation artifacts;
- explicit missing/unknown output where extraction cannot prove a fact.

The Reflection representation is descriptive only: it cannot grant authority, availability, authenticated Account truth, or evidence maturity.

For the canonical journey it must answer:

- What is Claude here?
- Which Accounts exist?
- Why do I need to choose?
- What is `prompt.send`?
- What data would leave the local boundary?
- What does SIMULATED mean?
- Why is this command not READY / READY?

A model may phrase grounded claims if used, but no model output may invent capability, Account state, authority or evidence.

No separately authored Wiki page may be required to make the canonical semantic records explainable.

## 11. Virtual execution/evidence

The `prompt.send` realization is virtual.

It must:

- accept only validated committed commands;
- emit explicit start/attempt/result events;
- bind events to command/world/revision identity;
- produce a deterministic receipt;
- label source/maturity as simulation;
- never set fields that imply authenticated provider observation;
- support at least one deterministic failure path.

A receipt should make the distinction machine-readable, not merely prose.

## 12. Replay

A pinned D1 run must capture enough to replay:

- World snapshot/version;
- semantic registry version;
- language/interpreter version or digest;
- input revisions;
- semantic edits;
- command identity;
- authority fixture/decision;
- virtual realization version;
- event/evidence sequence.

For identical pinned inputs, replay must produce the same canonical command and evidence digest except for explicitly excluded presentation timing.

## 13. Test gates

D1 cannot be declared complete until these are automated:

1. **False READY:** unresolved required Account can never be READY; corpus U1 fixed.
2. **Explicit target precedence:** explicit Work beats any default/prior.
3. **Ambiguity honesty:** two compatible Accounts remain unresolved unless an explicit visible rule resolves them.
4. **Unknown target:** unknown/incompatible Provider/Account cannot execute.
5. **Quoted payload:** Provider/Account words inside payload do not retarget the command.
6. **Revision safety:** late result for revision N cannot replace N+1.
7. **Typed/clicked parity:** equivalent correction gives equivalent command digest.
8. **Projection purity:** changing visual treatment cannot change command digest.
9. **Reflection/Wiki grounding:** removing or structurally changing a reflected capability/parameter/realization changes or invalidates the corresponding current help claim; reflected facts remain source-bound and read-only.
10. **Authority separation:** interpretation/selection alone cannot grant consent.
11. **Simulation boundary:** virtual receipt cannot satisfy a live-evidence predicate.
12. **Replay determinism:** pinned complete journey replays identically.
13. **Regression:** existing `bun test plugins/vivim-nlcl` and `omega:quick` remain green.

## 14. Release artifact

D1 should leave:

- executable source;
- one documented launch command;
- deterministic fixture Worlds;
- semantic/command schema or code contracts;
- scenario corpus;
- UI/product twin;
- minimal source-bound Reflection extractor/graph + contextual Wiki/help slice;
- virtual executor;
- replay runner;
- tests;
- machine-readable D1 evidence summary;
- brief architecture note recording what was reused, adapted, invented, and still open.

The evidence summary must say **SIMULATED** prominently.

## 16. Architecture freedom

This specification fixes the **observable D1 behavior and evidence gates**, not the implementation architecture.

The builder may reuse/adapt existing `vivim-nlcl`, `vivim-mind`, `vivim-law`, Vault, web/CLI surfaces, or build a bounded experimental composition where that is faster and cleaner.

Prefer reuse of proven semantics over clean-sheet replacement.

Do not make an experimental implementation permanent Ω architecture merely because it ships D1.

## 17. D1 completion statement

The only acceptable completion claim is approximately:

> D1 demonstrates the first-release semantic interaction end to end against synthetic, source-labelled Worlds and a virtual `prompt.send` realization. Interpretation, ambiguity, correction, command validation, contextual help, authority fixture, simulated execution, evidence and replay are executable and tested. No live Provider/Account/browser capability is claimed.

Anything stronger requires separate evidence.
