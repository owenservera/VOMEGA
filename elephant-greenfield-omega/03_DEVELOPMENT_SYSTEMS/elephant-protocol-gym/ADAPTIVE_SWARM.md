# Adaptive Elephant Swarm — Parallel Self-Organization to MVP v0.5

**Status:** OWNER-REQUESTED EXPERIMENT DESIGN / READY-TO-LAUNCH PROMPTS, **NOT LAUNCHED, NOT AN IMPLEMENTED ORCHESTRATOR**. Date: 2026-10-11.
**Scope:** exploratory, elastically parallel Elephant system self-organization, self-articulation and self-testing of the gap from the protected original baseline to the *updated* minimum MVP v0.5 requirements.
**Authority:** [Gym D1–D4 launch policy](LAUNCH_POLICY.md), [SDK self-hosting objective](SDK_SELF_HOSTING_DOGFOOD.md), [visual parity contract](CORE_VISUAL_LANGUAGE.md) and [all-state turn publication](../../01_EXPECTED_OUTPUTS/02_EVERY_TURN_PUBLICATION_CONTRACT.md).

## 1. Core research question

**Can an Elephant organization discover, articulate, test and continuously improve its own operating protocols and developer toolchain to deliver the smallest evidence-proven useful VOMEGA MVP v0.5, while adapting to changing owner objectives?**

A successful result is **not** a grand organizational proposal or an inventory of missing code. The organization must produce *observed evidence about its own performance*, discover what capabilities it needs, revise team topology and protocol through falsifiable experiments, and show that improvement through the same **command → machine meaning → Human/Wiki/3D visual intelligence → guarded tool action → actual evidence → feedback → proposed change → replay** loop the SDK exposes to humans.

**The Elephant system is the first product and the principal test corpus until its core operating model and the semantic SDK are sufficiently validated.** The provider-facing MVP remains a continuously visible end-to-end target, not permission to defer core dogfood indefinitely.

## 2. Two-layer requirement baseline — no silent drift

### Immutable comparison basis

Use the historical [Greenfield Ω simulated Alpha/Beta/Gamma seed](../../00_CORE_BASELINE/02_GREENFIELD_OMEGA_SEED.md) as an *unchanged* cross-architecture control. Its historical benchmark is not the current MVP and cannot be overwritten or retroactively judged against newly-added requirements. Tests on this basis report SIMULATED and use the existing fixed scope.

### Mutable owner objective, append-only lineage

Use the authoritative [MVP v0.5 North Star](../../../mvp/NORTH-STAR.md) **plus an explicit, versioned requirement overlay for the Gym**. The North Star defines desired functionality; its [pinned research mirror](../../00_CORE_BASELINE/04_MVP_V0_5_PRODUCT_NORTH_STAR.md) remains a historical snapshot. Never silently update the mirror or rewrite old experiment scores.

The **Gym overlay** adds/reprioritizes confirmed requirements from subsequent owner directions:
- Semantic SDK is **TypeScript-first** and must expose the developer tool capabilities used to inspect/build/test/improve itself (tool adapters are replaceable, not all in one mandatory binary).
- First major experimental corpus is **Elephant's own source, context, coordination and protocol**, yielding runnable, independently witnessed explanations and self-improvements via Command → Wiki → Test.
- **Effectively infinite 3D canvas** is the shared human-facing development shell, initially sparse with a floating text box.
- The **human–machine shared real-time semantic/execution manifold** preserves one source-bound meaning, Human/Wiki/machine/spatial parity and time/effect/status distinctions.
- **Core high-density visual intelligence language** must include a machine-readable visual projection. Users must be able to reprogram visual encodings without breaking command chains, obscuring material facts or bypassing authority.
- Native symbolic commands, 17 legacy glyph families, Reflection Migrator, existing devtools, D1 gates and legacy ideas are *reference controls/candidate building blocks*, not mandatory final architecture.
- **Enter publishes** the current semantic snapshot; external effect execution/consent and observable receipts are separate.
- **All maturity states** are published at the end of each actual development turn and research round. Evidence and explicit unknowns must survive independent Elephant handoff.
- Preserve the **product v0.5 user capabilities** (workspace, contextual Wiki, provider account registration/isolation, discovery, routing/fanout, controls, history). Development may prove first minimal slices before provider integrations; simulated external connections must be labelled as simulated.

These are requirement *outcomes*, not a mandatory compiler grammar, runtime, transport, fixed toolchain, WebAssembly, browser, UI framework, data store, process manager or ten permanent teams. The precise question of what counts as a completed minimum useful MVP must be justified by a demonstrated coherent vertical slice, not by deleting user capabilities from the destination.

### Owner-drift reconciliation

Owner feedback or a new user requirement is an **event with source/time, intended interpretation, affected requirements, alternative readings, uncertainty, proposed acceptance tests, consequence/effort and explicit approval state**.

Experiments may autonomously update their **proposed backlog, task allocation, architecture candidates and test variants**. They must **not** autonomously rewrite the authoritative requirement overlay or pretend owner approval. A recognized new owner directive becomes tracked proposed/confirmed change; if ambiguous, list alternatives and provisional, reversible experiments. Keep old and new versions available for impact/replay. Human/Wiki representation of each changed requirement must be traceable to the same machine-readable intent, and the visual canvas cannot invent owner authorization.

## 3. Elastic parallel swarm, not prescribed organization

**“Unbounded” refers to an open and expandable *design space* and independent research streams, not infinite tokens, runaway workers or unlimited authority.** Start with six **independent, equal-baseline** research arms; each may recommend creating additional bounded sub-experiments, merging roles or retiring itself. Number of active agents, model/context selection and concurrency budget are learned empirically. A controller/operator reviews resource and authorization bounds, compares marginal independent evidence per unit of cost, and can cap/pause streams. No recursive self-spawn without explicit host budget and sandbox allocation.

Initial *hypothesis portfolios* (not departments):
- **S1 — Self-model and organization:** What must an Elephant know about itself, its context, capabilities, limitations, activity, obligations and resource use? Experiment with its own role/structure proposals, falsifiers and ablations; compare [Universal Elephant DNA](../../05_UNIVERSAL_ELEPHANT_DNA/README.md).
- **S2 — Semantic SDK / command → wiki:** Build/test the smallest genuine command that explains an Elephant source/protocol fact through machine and Human/Wiki projections; compare NLCL and source reflection controls.
- **S3 — Development automation and rapid learning:** Discover reusable tool adapters, mutation/replay/test automation, experimental feedback, test reliability and true cycle-time bottlenecks. Do not mistake generated test definitions for tests actually run.
- **S4 — Visual/manifold communication:** Discover high-density self-understanding visual grammar, machine visual spec, 3D representation and user reprogramming invariance. Compare pure words, glyphs, hybrid and spatial representations on same semantics.
- **S5 — Context/handoff and communication:** Reconstruct actual context load, source changes, requests, losses and recovery across independent Elephant sessions. Measure usefulness/effort against single-agent control; no invented peer telemetry.
- **S6 — Skeptical MVP feasibility / wildcard:** Independently bridge all changes to a minimally useful v0.5 slice, challenge essentiality, find integration and safety failures, propose a radically different organization or architecture, run negative controls and expose untested requirements.

**All arms must introspect their own protocols**, not just produce assigned subject-area artifacts. Organize on demand around the most important verified bottleneck. An arm may advocate its own dissolution or replacement.

## 4. The self-organization protocol: Observe → Need → Test → Reconfigure

Every development iteration, each arm answers six accountable questions:
1. **What is actually true of me?** Actual tools, context received, available source, consumed files/versions, successful/failed invocations, missing witnesses, work obligations, environment and limitations.
2. **What specific MVP/SDK/Elephant outcome is blocked?** Identify a requirement, current proof gap, dependency and its consequence, not just an interesting technology.
3. **What could fix it, and how would we falsify it?** Compare minimum two credible approaches, including reuse/current controls where available; unknowns are candidates not assumptions.
4. **What experiment can I run now?** Pin inputs and perform a tiny independently judgeable action; if no executor is available, classify NOT_RUN and describe the smallest runnable test rather than hallucinate.
5. **Should my own team/protocol/tooling change?** Propose **KEEP / SPLIT / MERGE / REASSIGN / RETIRE / ADD / REPLACE** with expected benefit, resource cost and blast radius. Treat untested reorganization as a hypothesis.
6. **Can a fresh Elephant understand and replay my finding using Command → Wiki and machine-readable evidence?** Generate a self-explanation grounded in the actual witness plus a reconstructable all-maturity pack.

Reconfiguration must be **transactional**: proposal → sandbox trial → matched control → independent referee → accept/reject → recorded revision with rollback. A host may authorize operational reallocation within budget; owner-relevant changes to shared canon or product objectives require explicit review. No long-lived owned branches: short-lived isolated worktrees permitted, consolidate approved verified changes to shared main.

## 5. Cross-stream learning without destroying independence

Round 0: all six arms receive the same pinned baseline and owner overlay, but **only their own arm-specific brief**; avoid exposing another arm's novel proposed architecture until first findings are sealed. Streams may read the same shared semantic source/tests but keep implementations independent.

Turn-close: every arm publishes its **complete capability inventory, including failed/incomplete/unchanged packs**, current self-model, known/unknown gaps, proposed requirements and reorganization, command↔wiki learning signal, methods and real test witnesses (or truthful NOT_RUN) through the existing publication contract. An arm with no progress publishes a heartbeat.

Round-close: independent referee compares proposals and results; separates evidence from eloquent narratives, surfaces contradictory claims and common dependencies, updates a **derived** cross-stream gap/dependency map, and publishes the source-grounded owner-facing summary. The referee does not automatically rewrite requirements or decide to certify its own designs.

Refeed: after first blind results, give approved reference/reuse arms access to winning or failed protocols; maintain sealed holdouts and source hashes. Compare fresh discovery vs legacy-seeded reuse vs integrated arm; no model self-judged score is ground truth. Count redundant duplicated work as a *cost*, except deliberate independent verification.

## 6. Gap artifact as live protocol intelligence, not a spreadsheet graveyard

Every reported gap links:
- **Requirement:** stable ID, current owner/baseline status and source, MVP relevance, behavior and falsifier.
- **Observation:** witnessed actual/failed behavior, current source/test/Elephant epoch and evidence class; UNKNOWN/NOT_RUN explicitly recorded.
- **Dependency:** which SDK/tool/Elephant/context/runtime capability is missing and what it blocks.
- **Hypotheses:** minimal options, including reuse and architecture wildcard.
- **Trial:** frozen controls, proposed minimal independent test, costs, risk, expected improvement and actual outputs.
- **Organization response:** which expertise/context/tools/peer help are needed; why split/merge/reassignment improves actual throughput.
- **Learning publication:** same immutable machine meaning, Human/Wiki explanation and visual signal (when available), with source and uncertainty.
- **Decision:** proposed, accepted for isolated lab, independently checked, or explicitly owner-approved for canon; actual fix/rollback status.

Do **not** build a second ontology or PM engine for these fields. They are conceptual required content that existing Gym run reports, capability packs and source/witness manifests can carry. Serialize where tools already support it.

## 7. Six research problems the swarm must expose early

A. **Can an Elephant correctly explain why one of its own tooling tests failed?** Pinned command, source, actual stdout/stderr and source-linked Wiki, not prose reconstruction.

B. **Can it modify its own protocol without breaking the prior witness?** Version a context-selection or handoff method in isolation, replay a control, detect losses and roll back if worse.

C. **Does its own self-model tell the truth?** Blind tests with a withheld source dependency, missing memory, unavailable private artifact, synthetic telemetry and changed file epoch. Refuse to pretend absent measurements are zero.

D. **Can visual style be changed without changing commands or hiding risks?** Re-theme icon/glyph/geometry while maintaining canonical digest, affordance semantics, and Human↔machine↔spatial parity.

E. **Does parallel organization outperform a solo agent?** Compare single-agent reference vs 2, 4 and 6 bounded arms and *adaptive* number under matching work/budget where possible. Measure validated outcomes/hour or per-cost, duplicate effort, coordination delays, false agreement and artifacts another agent can reproduce. The highest concurrency is not presumed best.

F. **Can it advance the v0.5 slice while proving these abstractions?** Preserve all target requirements in the overlay; demonstrate a real command to browse self-knowledge, inspect actual tests, and later a bounded simulated fanout without claiming provider accounts/browser automation exist. Test whether the same command/visual/Wiki/evidence contracts are product-general rather than hardcoded to the Elephant itself.

## 8. Optimization and stopping rules

Optimize **independently witnessed owner-relevant learning and working MVP capability per unit of end-to-end time/cost**, including integration, reviewer burden and context traffic. Separate discovery coverage, exact source comprehension, test reliability, handoff reconstruction, semantic parity, visual comprehension, tool execution success, failure detection, mutation kill rate, useful software increment and regression rate. Quantitative claims require denominators, source/witness, cohort, hardware/model/effort basis and MEASURED/ESTIMATED/UNKNOWN.

Avoid proxy traps: total agent turns, number of tasks created, lines of code, documents generated, claimed sophistication, number of agents, reduction in obvious error by answering UNKNOWN to everything, or beautified 3D renders alone are not sufficient.

**Per-stream stop/redirect:** a round has no falsifiable next test, no novel evidence, repeated unanswered tool limitations, increasing integration cost, or inferior utility to merged/solo control. Park with complete pack rather than leave a zombie stream. New agent streams require a purpose, owner-authorized budget, falsifier and clear dependency boundary.

**Phase 0 readiness:** one Elephant can demonstrate source-pinned SDK/tool self-knowledge through command/Wiki, a real bounded tool test with honest receipts, a witnessed semantic mismatch and improvement, honest own context/protocol inspection, safe visual customization parity and reproducible independent handoff. An integrated multi-Elephant variation must outperform (or justify itself against) a comparable simpler baseline on at least one meaningful measure without degrading safety. This is intentionally stronger than six independent essays and weaker than claiming full v0.5 provider integrations.

**MVP v0.5 readiness:** evaluate against the actual current product north star and overlay at its source/requirement epoch, including the smallest installable useful slice and subsequently remaining functionality. Claim only demonstrated capabilities; label integrations unavailable, mocked or partially implemented.

The first artifact is [STREAM_STARTER.md](adaptive-swarm/STREAM_STARTER.md); the second is a [machine-readable launch config/requirements overlay](adaptive-swarm/launch-manifest.json).
