# Universal Semantic SDK Governance — Everything That Is Code

**Status:** OWNER-DIRECTED END-STATE REQUIREMENT AND STAGED ADOPTION LAW; **NOT IMPLEMENTED OR CURRENTLY ENFORCED**. Updated 2026-10-11.
**Root:** [Elephant self-hosting SDK objective](SDK_SELF_HOSTING_DOGFOOD.md), [machine↔human parity](INITIAL_STATE.md), [core visual intelligence](CORE_VISUAL_LANGUAGE.md), [adaptive stream](ADAPTIVE_SWARM.md), [existing Rule 1](../../07_OMEGA_SEMANTIC_SOURCE_ARCHITECTURE/RULE_1_MACHINE_HUMAN_COEVOLUTION.md).

## The requirement is UNIVERSAL, not just Elephant settings

**Everything in this project that is code, a tool, an operating mechanism, a runtime capability, a configuration, an execution protocol, a source-driven action, or an instrument for development must eventually be represented and governed through the Semantic SDK's shared Machine ↔ Human command system.** That includes the machinery used to create the SDK and the command interface itself.

Examples—not a closed or exhaustive schema—include: TypeScript source modules; source builders/compilers; test/benchmark/evaluation runners; semantic grammar and compiler settings; generated Wiki and source/reflection indexers; context/memory/ingestion/flush/rotation; Elephant identity, context assignment and organizational topology; cross-Elephant messaging; ECP/communication protocols; experiment controllers and fan-out executors; isolation, canary/fence and oracle controls; continuous integration; permissions, policy, budget and evidence verification; visual language and custom theme/rendering; local CLI, IDE and adapters; tools used for source harvesting, dependency mapping and versioned release/packs; eventual provider/account/browser product functions.

This is not permission to expose secrets or directly edit arbitrary infrastructure. The SDK must faithfully represent both what is known and what is **not observable, unavailable, simulated, unauthorized, proposed, or immutable**. A tool not yet integrated is recorded as a coverage gap, not hidden or hallucinated.

## One self-hosting command-to-wiki-to-change path

For every target code/tool/protocol/configuration domain, the eventual same semantic circuit is:

```text
Human utterance OR Elephant utterance OR spatial semantic control
      ↓
Intent candidate(s) + grounded source/target and epochs
      ↓
Versioned canonical machine semantic publication
      ├── machine-readable command + visual assertions
      ├── human-readable Plain Reading + source-derived Wiki
      └── shared 3D canvas intelligence / uncertainty
      ↓
Status + permitted affordances + explicit effect/authority gate
      ↓
Authorized action / isolated test or rejected/not-run observation
      ↓
Actual tool output + versioned evidence/receipts
      ↓
Independent comparison and repair proposal
      ↓
Semantic change/reprogramming with revalidation and rollback
      ↓
Updated source/wiki/visual projections + every-turn capability publication
```

A *human and machine* share the same command meaning/evidence, not the same natural-language words or hidden cognition. Their projections must agree on material semantics (source, identities, targets, configuration, effects, uncertainty, authority, freshness, lifecycle and outcomes). The actual visual renderer must be independently checked against its machine-readable visual contract. Human-directed edit of a visual presentation must **not** silently mutate the underlying command chain; a meaning-bearing visual edit must emit a new semantic command revision and pass normal validation.

## Universal semantic-control coverage gate

A domain may be marked `INTERFACE_GOVERNED` only with an independently witnessed demonstration that:
1. **Discovery:** the SDK can identify the actual target implementation/source, version and available parameters/capabilities and expose genuine unimplemented/unknown areas.
2. **Read:** a person and an Elephant can ask questions through the same command interface and receive accurate, source-linked Wiki and machine-readable meaning.
3. **Propose:** any supported state/setting/behavior change produces a typed *proposed semantic edit* with explicit scope, expected effects, alternative meanings, dependencies, version basis and authority requirements.
4. **Act:** a permitted setting/tool/protocol change is dispatched **through the command system**, after applicable external/owner review. No `!`, UI glyph, model text or confidence score grants consent.
5. **Test:** the toolchain executes a real bounded relevant test where authorized; results include raw receipts, timestamps, changed basis/epoch, failed conditions and honest measured vs unknown costs.
6. **Parity:** machine command, human Wiki/Plain Reading, 3D visual affordance and actual witness agree on material meaning and authorization. Cosmetics/pan/zoom do not affect command digests.
7. **Replay/rollback:** independently re-run at the pinned source/config basis; reject or roll back destructive/unverified candidates and preserve prior results.
8. **Provenance and portability:** accepted, rejected, incomplete and failed capabilities are published under the existing [every-turn portfolio contract](../../01_EXPECTED_OUTPUTS/02_EVERY_TURN_PUBLICATION_CONTRACT.md). A fresh Elephant reconstructs a supported explanation from packs/source without hidden chat state.
9. **No bypass:** after a capability has passed the interface-governed gate, all *normal supported developer and Elephant edits* to that domain must use the semantic interface. A direct configuration/file mutation becomes a test failure unless under a separately documented, authorized emergency recovery/bootstrapping procedure. Repository/Git and host enforcement remain independent guardrails; SDK claims alone do not physically prevent bypass.

These are **capability-specific gates**, not a declaration that the current codebase has reached this state. Ordinary source control, safety tools and independent test witnesses retain distinct authority from explanatory projections.

## Phased rollout without circular deadlock

- **U0 — Indexed, NOT_GOVERNED:** discovered and source pinned; code/tools/knowledge may still be used directly with existing auth and evidence, to build the SDK. Missing coverage and bypasses are visible.
- **U1 — Explainable:** source/operational introspection and Wiki plus machine/visual projection; real proof labels, no fabricated executors.
- **U2 — Proposed edits:** version-bound typed config/operating-change proposals, impact and authority analysis; operations may be simulated/held.
- **U3 — Governed test:** bounded authorized action runs via semantic command, actual result/negative probes, parity, independent verifier and rollback.
- **U4 — Interface-required:** supported routine updates *must* use the canonical command interface; raw edits are auditable exceptions, with an explicitly scoped emergency recovery path.
- **U5 — Recursive self-hosting:** SDK, source compiler, Wiki generator, visual renderer, evaluator, publication tooling and Elephant swarm operating protocol itself reach U4, with independent escape/recovery and an external oracle to avoid self-certification.

**No broad “we are done” claim** until the coverage map identifies every relevant eligible code/tool domain; each domain has an independently warranted U-level, exact known limitations, source epochs and gap-to-gate. The owner may move the required minimum gate forward by area without freezing universal implementation choices. Safe bootstrapping remains possible before U4 and during a documented failure recovery.

## First executable demonstration

Start small but self-referential: `? explain SDK test runner` → actual source reference and command description in Wiki → `/test @sdk-runner` creates a version-bound semantic plan, not immediate arbitrary execution → authorize bounded harmless test → capture actual stdout/stderr and verify meaning/visual parity → `∆ @sdk-test-setting` produces proposed edit and same test replay → independently prove a direct bypass is detected (or mark NOT_IMPLEMENTED) → publish candidate pack.

Then apply identical control patterns to Elephant handoff/context policy, swarm orchestration, visual theme mapping, semantic lexer, developer build tooling, evaluation and release. **Do not implement separate hidden self-management APIs** if they would evade the eventual shared command/witness chain. Candidate adapters and standards remain open to competition and replacement.
