## I. The mission and the vision

We are testing a new development paradigm: instead of every AI developer repeatedly scanning thousands of project files and reconstructing architectural context, a worker asks a maintained, high-context AI session—an **Elephant**—for source-grounded domain understanding, historical reasoning, impact analysis, proposed implementation advice or patch review. An Elephant may retain a versioned domain context over multiple tasks; the active worker implements and independently verifies. We want to test whether this creates a measurable acceleration in **accepted useful software delivery** and generates novel, reusable engineering mechanisms.

The eventual architecture should be a provider-agnostic, source-verifiable cognitive service with dynamic routing, bidirectional artifact-rich communication, context residency, explicit flush/reconstitution, Git epoch freshness, auditable agent provenance, two-node disagreement handling, token economics, failure recovery and calibrated improvement loops. Treat every elegant proposal as a hypothesis. Source code, test results, observed runtime evidence and accepted decisions are truth; model context, memory and self-report are fallible derivatives.

**Experiment levels:** E0 = no Elephant, honest fresh-worker baseline. E1 = one genuinely live contextual Elephant service. E2 = two distinct *concurrent* Elephant sessions that may consult across source-domain boundaries. These are **not** the two master teams. At every level run two persistently competing **master implementation approaches**: Master A begins resident-context-first; Master B begins deterministic pack/rebuild/stateless-first. Let each strategy evolve independently with evidence.

In separate master contexts, let **each of the two masters** ingest all four outcomes and independently select, combine and collapse successful mechanisms into **its own** next candidate, reject failed approaches and explain evidence. Only after independent assimilation may they exchange bounded critiques or port small proven features. Keep both A-next and B-next runnable, meaningfully different, separately documented, benchmarkable and versioned. Do not select a permanent winner or merge masters into one design.
