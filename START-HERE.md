# Start Here — VIVIM-Ω Fresh Autonomous Build

This folder is deliberately small at the project-intent level and deliberately rich at the implementation level: the Ω baseline is already here, but the old agent-development machinery is not.

The purpose of this seed is to let a new ZCode project start from a known Ω implementation and enough durable product context to autonomously determine what to build next.

## Read these first

The project-level seed is now nine documents, each with a deliberately different job:

- **AGENTS.md** — operating mandate for the autonomous build.
- **START-HERE.md** — this orientation and documentation map.
- **VISION.md** — the long-horizon product proposition and durable IP candidates.
- **PRODUCT-ANCHOR.md** — the first tangible beta experience: a persistent environment with real provider webapps as usable external capabilities.
- **INVARIANTS.md** — inherited semantic, sovereignty, evidence, authority, continuity, and extensibility guardrails.
- **PROJECT-CONTEXT.md** — why Ω exists, how VIVIM evolved, and how to interpret the seeded corpus.
- **BUILD-FOCUS.md** — areas likely to deserve disproportionate investigation and engineering attention.
- **AUTONOMY.md** — explicit authority to create the development organization and change Ω when evidence warrants it.
- **ZCODE-CAPABILITY-SPACE.md** — the current ZCode capability substrate, release-derived capability trajectory, and autonomous DevOps boot sequence.

These documents are not equally authoritative:

**VISION** describes the durable destination.

**PRODUCT-ANCHOR** makes the destination tangible enough to build and test.

**INVARIANTS** records the distinctions and constraints that should survive changes of method.

**PROJECT-CONTEXT** explains the history and evidence behind the seed.

**BUILD-FOCUS** identifies where to investigate, not what implementation to choose.

**AUTONOMY** and **AGENTS** define how the fresh project is allowed to operate.

**ZCODE-CAPABILITY-SPACE** describes the external development substrate the fresh project can exploit and the boot sequence for designing its own DevOps.

## The central distinction

Do not confuse:

1. the product vision — what VIVIM is trying to become;
2. the product anchor — the smallest tangible environment that makes that vision real;
3. the current Ω baseline — what has already been implemented and proven to some degree;
4. the next build plan — what this new autonomous project should do next.

Only the first is the durable north star.

The second is a functional wedge intended to keep the build tangible.

The third is evidence plus reusable implementation.

The fourth must be freshly derived.

## The long-horizon / near-term relationship

The project should be able to explain this relationship simply:

**Long horizon:** sovereign semantic operating environment.

**Durable core:** human semantic control + personal semantic world + governed action + durable Work/proof/continuity + governed evolution.

**First tangible route:** persistent VIVIM environment → real provider webapp → human expression → semantic intent → governed browser execution → evidence → continuing local world.

The provider webapp surface is a wedge, not the final architecture.

The team should continuously test whether today's implementation can be replaced without destroying those durable properties.

## First pass

Treat the first pass as reconnaissance, not ceremony.

Establish:

- what the baseline actually boots and proves today;
- which architectural claims are enforced by code and tests;
- which important vision claims are still aspirational;
- which decisions are historical, superseded, or implementation-specific;
- whether the current product anchor is genuinely achievable from the baseline;
- which smallest complete user journey creates the most learning;
- where the largest value and architectural risks are;
- what development structure increases throughput rather than adding bureaucracy.

Then build the development system you actually need and start closing the highest-leverage gap.

## The seed is a launchpad, not a cage

There is intentionally no prebuilt ZCode team, workflow graph, board, roster, department tree, backlog, or old project-management structure.

The new project may create any of these if the work proves they are useful.

It should not recreate them merely because they existed elsewhere.

Likewise, Ω itself may be changed.

Preserve a durable product truth because it remains true, not because it happens to be represented by today's files.

## Using the repository corpus

These principles are embedded across the seed rather than defined as a separate architecture specification. `VISION.md` defines the durable strategic shape; `INVARIANTS.md` protects solution-selection constraints; `PRODUCT-ANCHOR.md` applies them to the first real route; and `AGENTS.md` / `AUTONOMY.md` make them part of autonomous architectural decision-making.

The seeded Ω implementation and the wider `docs/` corpus contain several kinds of material:

- product vision;
- ratified or near-ratified law;
- architectural proposals;
- evidence and test records;
- historical decisions;
- implementation detail;
- archaeology from older VIVIM systems;
- delivery plans;
- research packages;
- falsifiers and known gaps.

Do not flatten these categories.

The destination corpus is primarily a source of durable concepts, semantic separations, failure lessons, and useful falsifiers.

Its historical work plans, maturity scores, ownership structures, sequencing, and agent organization are not automatically inherited.

## Important freedom

You are not a migration script for the old VIVIM system.

The old VIVIM code and documents are useful as evidence, fixtures, examples, reusable mechanisms, and historical proof. They are not the blueprint.

The current Ω implementation is a strong baseline, but it is not sacred.

The new project should keep, replace, recombine, or delete mechanisms based on evidence.

## The ultimate test

The project should make increasingly large parts of this statement true:

> **I can use my local VIVIM environment to express what I want, operate my digital world through real capabilities, understand what it is doing and why, retain the resulting knowledge and evidence, and return later without losing continuity.**

The implementation behind that statement is allowed to change dramatically over time.
